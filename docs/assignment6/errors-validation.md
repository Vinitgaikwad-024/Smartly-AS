# Assignment 6 — Honest Responses, Errors and Validation

## Status mapping
| Situation | Status |
|---|---:|
| Successful read/update | 200 |
| Created resource | 201 + `Location` |
| Successful delete / OPTIONS | 204 |
| Malformed JSON syntax | 400 |
| Missing/invalid Bearer credentials | 401 |
| Missing resource/route | 404 |
| Booking overlap / invalid state transition | 409 |
| Unsupported request media type | 415 |
| Unacceptable response format | 406 |
| Failed conditional update | 412 |
| Field-level validation failure | 422 |
| Per-client request limit exceeded | 429 + `Retry-After` |

All API errors use `application/problem+json; charset=utf-8` with `type`, `title`, `status`, `detail`, `instance`, and stable `code`; field validation adds `errors[]` entries containing `field` and `reason`. Error messages avoid stack traces, SQL details, secrets, and raw partner fault payloads.

Validation is performed before booking creation. The API rejects invalid date/time intervals, unknown room IDs, missing fields, and overlapping active bookings. Transient outbound partner errors are retried with a finite timeout and bounded backoff; partner 4xx errors are not retried. `Retry-After` is emitted on 429. A 503 Retry-After response is not generated by the current in-memory API because it has no simulated maintenance/dependency-failure endpoint; do not claim that scenario is implemented.

See root `curl-transcript.txt` for generated local HTTP evidence. Re-run the transcript and regression tests after code changes. Rate limiting is process-local and is reset when the application restarts.
